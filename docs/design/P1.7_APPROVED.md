## B. Isolasi, reset dan runner (R2, R4)

`db_apotek_online_demo` harus memiliki nama yang berakhiran `_demo` **dan** tabel `environment_marker` yang berisi environment `demo`. Generator/reset memeriksa kedua guard sebelum operasi apa pun; jika salah satu tidak terpenuhi, proses berhenti tanpa fallback.

Reset hanya melalui CLI/credential demo: dry-run → preview jumlah per tabel/run → konfirmasi run ID → operasi child-first hanya atas row `demo_run_id` terpilih → rekonsiliasi → audit reset yang tetap disimpan. Row tanpa `demo_run_id` tidak pernah menjadi target reset. Akses web tidak memiliki endpoint reset.

Runner migrasi CI3 CLI tunggal memakai `schema_migrations(version, phase, checksum_sha256, status, applied_at, actor)`. Sebelum apply: kunci eksklusif, backup terverifikasi, dry-run, checksum file, pemeriksaan drift. DDL idempoten dan menguji `IF NOT EXISTS`; bila objek ada tetapi definisinya berbeda, runner berhenti—bukan melewati diam-diam. Lint menolak `DROP`, `TRUNCATE`, atau `DELETE` tanpa approval flag eksplisit dan target yang terbatasi. Migrator tidak mendapat `DROP DATABASE`; backfill memakai akun DML terpisah. Tidak ada migrasi otomatis saat web startup.

Gerbang wajib: verifikasi checksum/restore backup → dry-run → lock → lint dan checksum → apply di scratch → validasi → persetujuan fase. DB rollback adalah restore backup terverifikasi sesuai recovery plan serta menonaktifkan feature flag; uji rollback selalu di scratch. DDL MySQL dapat implicit commit, sehingga migration harus restart-safe dan merekam partial failure.

## C. Urutan generator dan data (R3, R7)

Generator adalah CLI CI3 dengan seed tetap, versi generator, tanggal relatif Asia/Jakarta, dan `as_of` yang dapat ditetapkan. Ia bergantung pada domain service P1.2–P1.6 (stok/reservasi, PO/receipt, retur, forecast, procurement) serta **BusinessClock yang dapat disuntik** untuk past-dating. BusinessClock disiapkan pada prasyarat Phase 0; generator tidak boleh menduplikasi aturan lewat raw INSERT. Implementasi generator baru boleh setelah service yang diperlukan tersedia dan diuji.

Setiap demo run punya ID unik; setiap row yang dibuat/diubah dalam run—termasuk master demo dan event turunan—menyimpan `demo_run_id`. Idempotency key deterministic per `(demo_run_id, scenario, event, ordinal)`. Hasil seed + `as_of` sama harus menghasilkan nilai bisnis yang sama.

Skenario wajib: fast/slow/no sales, seasonal, critical/overstock, near-expiry, sampel lead time ≥3 dan <3, PO parsial dan batal pascakonfirmasi, multi-supplier, PO sent belum confirmed, pembayaran gagal dan pembayaran sukses setelah TTL, reservation tertahan, quarantine/damaged/expired, hari stockout, retur direstock dan tidak direstock, unit empat tingkat, unit unverified. Generator merekonsiliasi total receipt/batch/balance/movement, reservation, payment/order, retur/demand, snapshot, lead time, dan Q sebelum run sukses.

Akun demo per role hanya dibuat pada DB demo. Password tiap akun dihasilkan acak saat generate, ditampilkan sekali ke operator, langsung di-hash, tidak disimpan plaintext, tidak dicatat ke log/dokumen dan tidak memakai password operasional.

## F. Saldo legacy dan gerbang unit (R5)

1. **Struktur dulu:** tambah tabel/kolom additive dan `demo_run_id` nullable; row legacy tetap NULL/unverified. Tidak mengubah alur lama.
2. **Backfill terbatas:** P1.2 balance legacy boleh merekam nilai jumlah mentah dari batch dengan `quality_status=sellable`, `quality_basis=legacy_unverified`, lokasi `Utama`, tanpa mengklaim bahwa nilai tersebut sudah base-unit. Cocokkan jumlah dengan sumber lama; jangan membuat receipt/movement baru. Reservation hanya ditautkan jika dapat direkonsiliasi.
3. **Kompatibilitas:** `legacy_unverified` menjaga visibilitas dan jalur legacy yang ada; row itu bukan input demand/forecast/Q atau receipt base-unit baru. Jalur lama tetap aktif untuk produk tersebut.
4. **Verifikasi satu kali P1.1:** petugas berwenang mencatat unit dasar, faktor, skala, bukti dan audit per produk. Konversi saldo menjadi base memerlukan migrasi/rekonsiliasi terpisah yang disetujui, membandingkan saldo sebelum/sesudah.
5. **Aktivasi bertahap:** hanya produk terverifikasi yang boleh memakai FEFO/reservation P1.2 baru, receipt base-unit P1.3, serta demand/forecast/Q yang mensyaratkan base. Produk belum terverifikasi tetap pada fitur lama/terbatas; tidak ada fallback konversi.

## H. Migrasi, uji, dan rollback

Urutan desain tetap P1.1 → P1.2 → P1.3 → P1.4 → P1.5 → P1.6; isolasi demo dan generator mengikuti domain service P1.2–P1.6 serta BusinessClock. Migrasi hanya additive. P1.7 bukan alasan untuk mengubah saldo/histori operasional.

Scratch test: backup terverifikasi → restore ke DB scratch terpisah → validasi baseline → dry-run/migration berfase → verifikasi checksum/FK/row counts/saldo/total transaksi dan sampel → uji reset/generator demo dengan dua guard → uji ulang idempotency → feature-off dan restore backup pada scratch. Jangan menghapus scratch DB yang ada.
