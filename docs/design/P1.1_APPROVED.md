# P1.1 — Desain Final untuk Ditinjau

**Cakupan:** unit produk, konversi, presisi, snapshot transaksi, harga, dan kompatibilitas data lama. Dokumen ini mencatat keputusan yang telah disetujui secara prinsip; implementasi tetap menunggu persetujuan terpisah.

## 1. Dasar desain dan status unit

Maksimal **empat satuan total per produk, termasuk base unit**. `products.unit_id` menjadi kandidat base unit setelah verifikasi manual. Setiap satuan alternatif memakai faktor langsung ke base, bukan konversi berantai.

Status unit dicatat eksplisit; terisinya snapshot saja tidak cukup untuk menganggap unit terverifikasi.

| Status | Tampilan | Pemrosesan |
|---|---|---|
| `verified` | Tampilkan unit, faktor, dan kuantitas base dari snapshot transaksi. | Konversi dan proses stok hanya jika konfigurasi serta validasi presisi sah. |
| `legacy_unverified` | Tampilkan sebagai data legacy dengan unit belum terverifikasi. | Workflow lama boleh berjalan tanpa konversi; jangan mengarang faktor atau kuantitas base, dan jangan gunakan untuk kalkulasi yang mensyaratkan base terverifikasi. |
| `unknown` | Tampilkan “satuan tidak diketahui”; akses histori tetap tersedia. | Blokir aktivitas yang mengubah stok atau membutuhkan konversi. Aktivitas lain yang tidak membutuhkan konversi tetap boleh. |

Transaksi lama tidak berubah menjadi `verified` hanya karena snapshot diisi belakangan. Snapshot historis tidak boleh di-backfill dengan tebakan.

## 3. Konversi dan validasi presisi

Tiga desimal adalah batas teknis awal, **bukan izin otomatis** untuk memakai pecahan. Presisi maksimal dikonfigurasi untuk setiap pasangan produk–unit. Tidak ada aturan bilangan bulat global.

Setiap transaksi menyimpan dua snapshot presisi:

- `input_quantity_scale_snapshot`: jumlah desimal maksimal yang diizinkan untuk unit transaksi yang dipilih.
- `base_quantity_scale_snapshot`: jumlah desimal maksimal yang diizinkan untuk base unit produk.

Validasi dilakukan berurutan:

1. Kuantitas input harus memenuhi `input_quantity_scale_snapshot`.
2. Faktor konversi harus positif.
3. Hitung konversi tepat dengan aritmetika desimal presisi tetap.
4. Hasilnya harus memenuhi `base_quantity_scale_snapshot` dan batas teknis tiga desimal.
5. Jika hasil tidak dapat direpresentasikan, transaksi ditolak dengan alasan yang jelas; tidak dilakukan pembulatan tersembunyi.

**Contoh:** faktor 10 Tablet per Strip, dengan input `0,25 Strip` dan skala input 2. Input valid; hasil matematisnya `2,5 Tablet`. Jika base unit hanya mengizinkan bilangan bulat (`base_quantity_scale_snapshot = 0`), transaksi **ditolak**, karena hasilnya tidak memenuhi presisi base unit. Jika base unit mengizinkan satu desimal, konversi dapat diterima.

Validasi tergantung operasi yang dilakukan:

- Transaksi divalidasi dari unit input ke base. Tidak perlu mensyaratkan semua saldo base bisa dikonversi balik tepat ke setiap unit alternatif.
- Tampilan saldo dalam unit alternatif yang hasilnya pecahan tak terwakili boleh memakai pecahan tepat atau nilai pendekatan berlabel “≈”. Angka tampilan bukan kuantitas transaksi dan tidak boleh digunakan sebagai saldo dasar.
- Memilih kuantitas transaksi dalam unit alternatif tetap diuji melalui konversi maju dari input itu.

Contoh tambahan: faktor 10, input `0,125 Strip` menghasilkan `1,250 Tablet`; konversi balik ke `0,125 Strip` juga tepat. Faktor tidak valid, hasil yang melebihi skala base, atau hasil yang melampaui tiga desimal ditolak tanpa pembulatan.

## 4. Harga dan snapshot transaksi

Harga harus jelas untuk tiap unit transaksi:

- Harga jual ditetapkan eksplisit untuk setiap pasangan produk–unit jual. Jika belum tersedia, transaksi ditolak tanpa fallback atau pengalian harga unit lain dengan faktor.
- Harga legacy hanya digunakan oleh workflow lama sampai satuan harganya diverifikasi; bukan otomatis harga semua unit alternatif.
- Harga PO baru berarti harga per unit PO dan disimpan bersama snapshot unit. Penerimaan beda unit dan alokasi diskon dibahas di P1.3.
- `stock_batches.purchase_price` dan kolom harga lama tidak ditafsirkan ulang sebagai biaya per base unit. Jika biaya base diperlukan, perlu kolom terpisah dengan presisi memadai dan aturan alokasi biaya yang disetujui.

Snapshot transaksi baru yang diusulkan:

| Kolom | Fungsi |
|---|---|
| `unit_id_snapshot` | Identitas unit transaksi. |
| `unit_code_snapshot`, `unit_name_snapshot` | Kode/nama unit saat transaksi. |
| `conversion_factor_to_base_snapshot` | Faktor yang digunakan pada transaksi. |
| `quantity` yang sudah ada | Kuantitas input; tidak dibuat duplikat kolom input. |
| `quantity_base` | Hasil konversi dalam base unit. |
| `input_quantity_scale_snapshot` | Presisi maksimal untuk unit input pada saat transaksi. |
| `base_quantity_scale_snapshot` | Presisi maksimal untuk base unit pada saat transaksi. |
| `unit_config_version_snapshot`, `unit_status_snapshot` | Versi konfigurasi dan status bukti unit saat transaksi. |

Pada PO, `received_quantity` tetap jumlah input dalam unit PO; tambahkan snapshot dan kuantitas base. Pada transaksi legacy yang tidak punya snapshot, nilai snapshot kosong tidak boleh dianggap sebagai verifikasi.

## 5. Perlindungan base unit dan kompatibilitas data lama

Perubahan `products.unit_id` diblokir melalui workflow biasa jika produk memiliki stok atau riwayat transaksi, sekalipun saldo kini nol. Perubahan hanya melalui rekonsiliasi/migrasi khusus yang disetujui, diaudit, dan menyertakan bukti konversi serta validasi saldo sebelum/sesudah.

Snapshot transaksi mempertahankan arti unit, nama/kode, faktor, presisi, dan versi meskipun master berubah. Unit yang dirujuk histori legacy tanpa snapshot perlu dipertahankan; hindari hard-delete atau rename yang dapat menyesatkan label histori.

Produk `legacy_unverified` tetap memakai workflow lama tanpa konversi. Untuk produk `unknown`, transaksi stok baru atau operasi konversi diblokir, tetapi histori dan aktivitas non-konversi tetap dapat diakses. Tidak ada backfill kuantitas base dengan faktor tebakan.

## 6. Keputusan yang ditetapkan

1. Maksimal empat satuan total per produk, termasuk base unit.
2. `products.unit_id` menjadi kandidat base setelah verifikasi manual; faktor konversi langsung ke base dan spesifik per produk.
3. Snapshot unit, faktor, kuantitas, status, versi konfigurasi, dan **kedua nilai presisi** diperlukan pada transaksi baru.
4. Data lama yang belum terverifikasi tidak dikonversi otomatis; snapshot yang diisi belakangan tidak membuatnya verified.
5. Tidak ada pembulatan tersembunyi. Batas teknis awal tiga desimal; presisi input dan base dikonfigurasi terpisah per produk/unit. Pecahan tidak dibatasi secara global.
6. Produk `unknown` diblokir hanya untuk aktivitas yang mengubah stok atau membutuhkan konversi; histori dan aktivitas non-konversi tetap dapat diakses.
7. Harga jual eksplisit per produk–unit; tidak ada fallback. Harga legacy hanya untuk workflow lama sampai unit harganya diverifikasi.
8. Penerimaan dengan unit berbeda dan alokasi diskon ditunda ke P1.3; kebutuhan snapshot tetap berlaku.
9. Unit resep tidak diasumsikan sama dengan unit produk; pembahasannya ditunda ke desain resep/dispensing.
