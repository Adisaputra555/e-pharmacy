## D. Aturan final

**Perdagangan dan status histori**

- Awal diperdagangkan adalah penerimaan stok sellable pertama, timestamp bisnis Asia/Jakarta. Override manual wajib alasan, actor, waktu, nilai lama/baru.
- `product_trading_periods` merekam interval aktif/jeda; satu bulan lengkap hanya bulan kalender penuh yang seluruh harinya berada dalam interval aktif. Tanpa bukti penerimaan/override: `Data perlu diperiksa`.
- Prioritas status: `Data perlu diperiksa` > `Belum cukup data` > `Tidak ada penjualan` > `Cukup data`.
- Unit belum diverifikasi tampil sebagai badge terpisah; tidak mengganti label histori. Base demand/Q tetap menunggu verifikasi sesuai P1.1/P1.6.

`Belum cukup data` berarti bukti perdagangan menunjukkan kurang dari tiga bulan kalender lengkap; `Tidak ada penjualan` hanya jika tiga bulan lengkap dan net demand 0; `Cukup data` jika tiga bulan lengkap, sumber konsisten, dan net demand positif. Status prioritas tertinggi menang. Badge unit belum diverifikasi tidak mengubah label histori, tetapi base D/forecast tidak diterbitkan sebagai base unit sampai konversi terverifikasi.

**Demand dan waktu**

Demand tidak bergantung channel; channel dipakai untuk return eligibility P1.4. Order lunas bila total amount payment berstatus `paid` mencapai `orders.total`. Demand dihitung per order dengan `EXISTS` payment paid agar item tidak tergandakan. Sale month adalah `MIN(paid_at)` dari payment paid. Pembatalan setelah paid mengurangi demand melalui correction/return adjustment di bulan sale asal; refund tidak mengurangi demand lagi.

Sumber bulan adalah `paid_at` Asia/Jakarta. Paid timestamp null tidak diganti `orders.created_at`; status data menjadi `Data perlu diperiksa`. Aplikasi memakai Asia/Jakarta; pembacaan/penulisan DATETIME harus konsisten pada zona bisnis tersebut.

**Forecast, coverage, dan snapshot**

`D = net demand 3 bulan lengkap ÷ 3`; forecast 1/3/6 bulan = `D × 1/3/6`. Hanya status `Tidak ada penjualan` (tiga bulan lengkap dan demand 0) menampilkan D=0 tanpa pembagian nol. Status tanpa riwayat cukup dan konflik sumber mengikuti prioritas di atas. Net demand negatif/adjustment berlebih adalah `Data perlu diperiksa`.

Coverage = usable stock P1.2 ÷ D. Batas tidak berubah: ≤1 kritis, >1–3 perhatian, >3–6 ideal, >6 overstock. Stok merah non-expired tetap usable; hanya tampilkan kuantitas berisiko sebagai warning/skenario terpisah. Stockout adalah flag turunan snapshot harian usable=0, bukan event atau lost demand.

Snapshot harian dijalankan oleh CLI CodeIgniter 3 melalui Windows Task Scheduler setelah penutupan hari bisnis. Tiap tanggal yang dijadwalkan memiliki status completed/failed/missed; hari terlewat ditandai missed, tidak di-backfill dari ledger yang tidak lengkap. Forecast snapshots append-only dibuat hanya saat run procurement, run manual, atau run bulanan.

Backtest rolling-origin MAE/WAPE hanya offline di data demo; WAPE tidak terdefinisi bila total actual 0. Tidak ada klaim akurasi produksi, trend, atau AI.

## H. Kriteria penerimaan

1. Bulan lengkap berasal dari interval aktif; test start/pause/override dan bulan parsial.
2. Status mengikuti prioritas final; unit badge tidak menimpa label histori.
3. Demand independent dari channel; return eligibility tetap memakai aturan channel P1.4.
4. Lunas, `EXISTS`, `MIN(paid_at)`, partial payments, cancellation setelah paid, dan refund diuji tanpa duplikasi atau fallback tanggal.
5. Test pergantian bulan Asia/Jakarta 23:59→00:00.
6. CLI snapshot harian idempoten; hari terlewat/failed ditandai; usable=0 hanya warning.
7. Forecast snapshot hanya dibuat pada procurement/manual/monthly run dan tidak menimpa snapshot sebelumnya.
8. Perbandingan live 3 bulan dan 90 hari menghasilkan nilai pada tabel B; unit legacy tidak dilabeli base unit.
9. Backtest offline/demo menguji MAE dan WAPE; total actual 0 menghasilkan WAPE tidak terdefinisi.
